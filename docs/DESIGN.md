# 設計文書: 誤送信の根本原因と対策マッピング

## 1. 誤送信はなぜ起きるか

個人情報漏えい事故の報告において、メール誤送信は不正アクセスと並ぶ最大級の原因
（JIPDEC 集計で漏えい事故の 3〜4 割）。発生メカニズムは大きく 4 類型:

| 類型 | 具体例 | 発生機構 |
|---|---|---|
| A. 宛先の取り違え | オートコンプリートで同姓の別人・別会社を選択 | **選択ミス**（一覧の隣を選ぶ・思い込み） |
| B. 公開範囲ミス | BCC にすべき一斉送信を To/Cc で送る | **手段の選択ミス**（知識不足・急ぎ） |
| C. 内容物ミス | 添付忘れ・別人宛ファイルの添付 | **注意資源の枯渇**（マルチタスク） |
| D. 打ち間違い | `gmial.com` などの typo ドメイン | **入力ミス** |

共通する根本原因は「**人間の注意力は毎回は使えない**」こと。
そして従来型の対策（毎回の確認ダイアログ）は、注意資源をさらに浪費して
**形骸化**する。安全工学でいう「警報疲れ (alarm fatigue)」である。

## 2. 設計原則

1. **正常時は妨げない** — 誤検知コスト（手間）をゼロに近づけることで、
   警告が出たときの信号価値を最大化する
2. **差分だけを確認させる** — 「今回いつもと違う点」だけを、理由つきで提示
3. **確認は一度だけ** — 確認済みの事実（宛先・組み合わせ）は学習して二度と聞かない
4. **すり抜け経路を塞ぐ** — ボタン・キーボード・送信してアーカイブを全て横取り
5. **壊れ方まで設計する** — セレクタ全滅時も Gmail は無傷。宛先が読めなければ
   フェイルセーフの目視確認を出す

## 3. 原因 → 検知ルール対応表

| 根本原因 | 検知ルール | 実装 |
|---|---|---|
| A. 取り違え | 初めての宛先を一度だけ確認 | 履歴照合（`chrome.storage.local`） |
| A. 取り違え | 既知アドレスとの酷似警告 | 編集距離 ≤2（ローカル部/全体） |
| A. 取り違え（既知同士） | 普段の宛先と酷似・低頻度の既知宛先を一度だけ確認 | 頻度非対称（相手側 ≥3回 かつ 2倍以上）+ ペア確認の学習 |
| A. 取り違え（内容照合） | 本文の宛名（〇〇様）が宛先に居なければ警告 | 異体字正規化 + 姓ローマ字辞書 + 慣用句ブロックリスト |
| A. 紛れ込み（文脈照合） | 同じ件名の過去送信に居なかった宛先を警告 | 件名ハッシュ→メンバー履歴（件名自体は保存しない） |
| A. 混在 | 初めての「外部ドメインの組み合わせ」警告 | 組み合わせ履歴（自己沈静化） |
| B. BCC忘れ | To/Cc の外部宛先 ≥N で BCC 提案 | 閾値は設定可能（既定 5）。フリーメールの From は全宛先を外部扱い |
| D. typo | 既知/有名ドメインとの酷似警告 | 編集距離 ≤2 + 主要ドメイン辞書 |
| （すり抜け） | クリック/キーボード/送信アーカイブ横取り | window capture 段イベント |
| （形骸化） | 異常時のみダイアログ・異常カードのみ個別確認 | リスクベース UI |
| （誤検知削減） | 自社ドメイン宛は宛先チェック対象外 | From ドメイン判定。フリーメールでは無効 |

### 「既知の宛先への取り違え」への多層防御

「前に送ったことのある別人」への誤送信は履歴照合だけでは検知できない
（どちらも正当な履歴を持つため）。そこで独立な3つのシグナルで検知する:

1. **頻度の非対称性** — 普段 sato@（50回）に送る人が saito@（1回）を選んだら一度だけ確認。
   「別人」と確認したペアは記憶し、以後は出さない
2. **本文の宛名** — 冒頭の「佐藤様」が宛先の表示名・アドレスと一致しなければ警告。
   一致すべき相手が履歴に居れば「もしかして」として提示
3. **スレッドの文脈** — 同じ件名でのやり取りに、過去に居なかった宛先が現れたら警告
   （宛先が全員入れ替わっている場合は同名件名の別件とみなして黙る）

それでも残る盲点（頻度が拮抗し、宛名も件名も手がかりが無い場合）は原理的に
コンテンツ理解なしでは検知不能であり、素通しトーストへの宛先表示（最後の目視）と
Gmail 本体の送信取り消し（最大30秒に設定推奨）を最終防衛線とする。

## 4. 学習モデル

- `recipients[email] = {count, lastTs, name}` — 一度でも「確認して送信」した宛先は既知
- `domains[domain]` — 既知ドメイン
- `combos["a.jp|b.jp"]` — 同時送信したことのある外部ドメインの組み合わせ（To/Cc のみ、BCC は除外）
- 上限 3000 件（LRU で剪定）。導入直後は確認が多いが、数日で収束する
  （= 「確認は各宛先につき一度だけ」）

## 5. 意図的な非対応（スコープ外）

- **Gmail 本体が持つ機能は実装しない**: 添付忘れの検出（Gmail 純正機能あり）、
  宛先ゼロのブロック、アップロード中の送信ブロック。件名なし・To なしの注意も
  漏えいと無関係なため持たない。この拡張は「宛先の取り違え・漏えい」だけに集中する
- 予約送信（「送信日時を設定」）経路の横取り — 今後のバージョンで対応予定。既知の制限として文書化
- Gmail 連絡先のインポートによる履歴シード — OAuth 権限が増え「権限は storage のみ」の
  プライバシー特性が崩れるため不採用
- 本文全体の内容理解（誤った相手に見せてはいけない内容の検知） — ローカル処理では
  原理的に困難。宛名照合・スレッド文脈・頻度非対称の3シグナルで代替する。
